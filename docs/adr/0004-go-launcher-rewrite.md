# Go Launcher with a Container Runtime Seam

`claude-contained` and `claude-docked` are two ~1,970-line bash scripts whose `diff` is 240 lines, almost all of it cosmetic: help text, `container list` versus `docker ps`, two shapes of `inspect`, the DNS default, Docker's Zellij labels and its platform-branched SSH socket. Every feature had to be written twice and kept in lockstep, enforced only by test suites that loop `for target in claude-contained claude-docked`. Nothing structural kept the two in agreement — a change applied to one and forgotten in the other was caught by a test if a test happened to cover it, and otherwise not at all. The launcher is replaced by a single Go binary with a container-runtime seam: one runtime-agnostic description of the intended run, rendered to a command line by an Apple Containers backend and a Docker backend, with every operation that genuinely differs — listing containers, reading a container's environment, ensuring the runtime is up, building the image, forwarding SSH — behind that interface and everything else living once, above it.

The runtime is chosen by the basename of `argv[0]`: one containing `dock` selects Docker, anything else Apple Containers. A flag would have been the obvious alternative and is the wrong one while the bash launchers are still the oracle, because any flag they do not recognize is itself a divergence in the unknown-flag path. Bash selects its runtime by *being a different file*, so the port does the same: the build emits `bin/claude-go` plus a `bin/claude-go-docked` symlink. Ticket 09 layers explicit selection by flag and environment variable on top, with `argv[0]` as the fallback. Ticket 11 resolves this for good (D1): once both runtimes install under the same program name, `argv[0]` can no longer be the primary mechanism, so it survives only as a compat affordance — a user who symlinks `claude-docked` to the installed binary, or still has one from before the launchers were unified, keeps selecting Docker that way — and as how the shell test suites drive the Docker runtime as a target path.

Ticket 09 revised that last sentence in one respect: `argv[0]` is no longer the *final* fallback, the host platform is. Selection is `--container-runtime`, then `CLAUDE_CONTAINED_RUNTIME`, then an `argv[0]` basename containing `dock`, then Apple Containers on macOS and Docker everywhere else. A basename without `dock` is not a selection at all, because "not docked" cannot mean Apple Containers on a host that has none — which is what the old unconditional default asserted. The unknown-flag divergence the paragraph above worried about resolved itself in ticket 11: with the bash launchers retired there is no second implementation to diverge from, so `tests/arg-parsing.test.sh` now asserts only that Go honors `--container-runtime`, unconditionally. An `apple` selection off macOS is refused with exit 2 before anything touches the host, which is what allows the Apple backend's runtime-liveness check to assume a macOS host with no defensive branch.

Plan building is a **resumable pure function**. Prompt answers are inputs to it, never outputs, because the answers change the plan in ways that are not local: declining to mount a linked worktree's main repository removes a mount *and* drops that repository from `GIT_PROTECT_DIRS`, which is the only input to the in-container sandbox's writable-path policy. The interleaving of prompts and mutations is behavior too — bash creates the persistent directory set before it asks about the `node_modules` overlay, so a user who declines the second prompt has already had the first batch applied. `Build` therefore returns the mutations determined *so far* plus the next question, and is called again with the answer; because it is deterministic in its inputs, the re-emitted prefix is identical and the driver skips it by index. Mutations are inert value types, so a test can assert an entire plan — every step in order plus the final run — without starting a process or touching the filesystem.

The in-container scripts stay shell. `image/entrypoint.sh`, `srt-settings.sh`, `srt-run.sh`, `shell-run.sh` and the `zellij-*.sh` helpers run inside the image, where bash is a given; they carry none of the duplication that motivated this rewrite, and rewriting them would add a second binary to the image and a cross-compile step to the build for no benefit.

Equivalence is proven before anything is deleted. The differential harness compares the Go binary against a bash launcher across runtime argv, stdout, stderr, exit status and a post-run filesystem manifest. Ticket 11's gate passed clean across the entire 59-entry corpus for both container runtimes at commit `973eeff`, and the bash launchers were deleted immediately after: the tracked `claude-contained` and `claude-docked` are gone from the repository root, and the Go binary now builds under the primary name instead of `bin/claude-go`. The retired scripts are recoverable with `git show 973eeff:claude-contained` (and `:claude-docked`) if a regression ever needs the oracle back; ticket 12 converts the corpus itself into golden test data, which is the long-term replacement for that oracle.

## Consequences

- The module declares no third-party dependencies, and git stays a subprocess. Worktree listing, the common-directory lookup and the on-disk lock files are the most safety-critical behavior in the launcher, and a library's model of them may not match `git`'s.
- `bin/`, `cmd/`, `internal/`, `go.mod`, `Makefile` and `.scratch` are excluded from the image build context. A multi-megabyte binary shipped to the builder is pure waste. See `CONTRIBUTING.md`'s "Keep the Dockerfile Small" section for the operative constraint and the full exclusion list -- this is the rationale, that is the one canonical place it is enforced.
- Paths not yet ported exit **3**, a status neither bash launcher uses, so the differential harness reports them as divergences rather than letting them pass as matching errors. Two of those guards are not keyed to a flag — the project env file and worktree auto-locking are reached with no flag at all, so a flag-keyed check would let them diverge silently. Ticket 10 removed the last such guard (`-R`/`--rebuild`), so nothing in the Go launcher produces status 3 any more; the status stays retired rather than reused for a new meaning.
- The *program* name is now a single constant, `runtime.ProgName`, used by both Profiles (ticket 11) -- there is no longer a second program name to embed. The image tag `claude-contained:latest`, the "reserved by claude-contained" rejection and the rebuild notice are the separate *product* name and stay literal in both runtimes regardless. The help texts remain two literal copies, not a template: they still differ in the description line, the `--dns` line, an entire DNS paragraph, a Docker-only "Build the image" block and one example's trailing comment. Ticket 11 unified the program name across both, so the examples are now identical apart from that comment -- a template would still buy less than it costs, because what remains differing is prose, not structure.
- The launcher does not `exec` the runtime. It runs the container in the foreground, regains control to run its cleanup, and exits with the container's own status.
- `main` does nothing but `os.Exit(run(...))`. Deferred cleanup does not run on a direct exit, and the launcher's cleanup releases worktree locks that, left behind, would block the user's next run — so every failure path returns rather than exiting.
- `CONTEXT.md` is the naming source: *project directory*, *extra mount*, *container runtime*. `Backend`, `Engine`, `Driver` and `Provider` are on its avoid list, so the seam is `Runtime`, not any of those.
- Two porting hazards are pinned by tests. The folder-name sanitizer trims dashes *before* truncating, so truncation can legitimately leave a trailing dash; its golden table was produced by running the bash function rather than by reading it. Path resolution is tolerant of paths that do not exist — it is applied to mount paths with no prior existence check — so `filepath.EvalSymlinks`, which errors on a missing component, is deliberately not used.
- Two deliberate divergences are documented rather than reproduced. `sanitize_foldername` with a leading-dash argument leaks BSD `basename`'s usage text to stderr; the port matches the result (`root`) and emits nothing, because that text is platform-specific and would not survive a Linux host. And the sanitizer's lowercasing follows the UTF-8 locale behavior of `tr`, which is multibyte-aware, rather than the byte-oriented behavior it has under `LC_ALL=C`.
- **The host platform is injected, not read at each use site.** `internal/runtime.Platform` is handed to `NewApple`/`NewDocker` at construction, and `runtime.GOOS` is read exactly once, in `HostPlatform()`. This is a testability seam, not a deep module: it hides nothing, and deleting it would move complexity rather than concentrate it. It is nonetheless necessary, because `GOOS` is a compile-time constant for a whole test binary while four behaviors branch on it (the default runtime, the SSH forwarding form, the host-gateway mapping, and the runtime-liveness check) — and CI runs `make quality` on Linux while development happens on macOS, so inline reads make the macOS arms unreachable in CI and the Linux arms unreachable locally. It is threaded through constructors rather than held in a package variable because a package variable is global mutable state shared across tests, and because threading it into `runWith` is what stops `cmd/claude-contained`'s tests from silently selecting Docker — and reaching CI's *real* daemon — once the default became platform-aware. There is no zero-argument constructor: it would quietly build the unnamed-platform behavior in a caller that meant to say Darwin. `cmd/claude-contained/probe.go` keeps its own `GOOS` read, which answers a different question (is the host already Linux, so the `node_modules` overlay is pointless); do not unify them.
- **A runtime capability difference is data on `Profile`, not a method.** `Profile.HostForwardNotice` carries the exact stderr lines shown when `-H` is used on a runtime that cannot reach host services bound to `127.0.0.1`; empty means the runtime forwards them properly. `NotRunningPrompt` was already a runtime-specific literal message, so this introduces no new concept, and it keeps `plan.Build` pure — a method would force `Build` to hold something with I/O attached. The notice is emitted as a `Print` **step** at bash's exact position in the stderr stream, because `Build` is replayed on every prompt round and printing directly would repeat the notice once per round. It is a notice and not a refusal because `-H` is genuinely useful on Apple Containers for host services listening on `0.0.0.0`.
- **`claude-contained` carries the identical `-H` notice.** This is the one time the rewrite has modified an oracle, and it means the two bash launchers now intentionally differ by two stderr lines. It was necessary: the differential harness compares stderr byte for byte against the *matching* launcher, has no per-target expectations, and ticket 11 gates deleting the launchers on a clean run across the whole corpus — so a Go-only notice would have failed the host-forward corpus entry on the Apple pair with no way to express the exception.
- **The `help_*.txt` fixtures are the source of truth for `--help` text; there is no bash script left to diff them against.** Each carries a `--container-runtime NAME` option line and a Behavior bullet describing the selection order, and (ticket 10) a `--build-context DIR` option line and its own Behavior bullet describing the resolution order -- additions bash never had. Changes go through the `.txt` files directly and the assertions in `TestHelpDocumentsRuntimeSelection` and `TestHelpDocumentsBuildContext` (`internal/runtime/runtime_test.go`), which is what makes the difference executable instead of a comment that can drift.
- **Build-context resolution self-locates with `os.Executable()`, never `argv[0]`.** `find_build_context` (`claude-contained:507-521`) relies on `$0` being the full script path even for a `PATH` lookup — a property the kernel guarantees bash but a compiled binary's `argv[0]` does not have. Resolving `argv[0]` for a `PATH`-invoked Go binary would anchor the search at the current working directory, i.e. at whichever project the user happens to be in, rather than at the launcher's own install location; the pre-ticket-10 `checkForUpdates` had exactly this bug. `os.Executable()`, followed by the same tolerant `ResolvePath` every mount path already gets, reproduces bash's guarantee for a compiled binary. Resolution order is `--build-context`, then `CLAUDE_CONTAINED_BUILD_CONTEXT`, then self-location, then the enclosing Git repository — but unlike `runtime.Select`, an *explicit* source (the flag or the variable) that names a directory with no Dockerfile refuses rather than falling through to the next source: a runtime name is a choice among two known values, while a build context is an assertion about the filesystem, and silently building some other directory under the `claude-contained:latest` tag would be worse than an error.
- **The update notice is deleted from all three launchers, not corrected.** It resolved its own checkout, ran an unbounded `git fetch` on every successful exit while the launcher still held the worktree auto-locks, and told the user to `git pull` — advice that updates sources, not the compiled binary, and is silently inert for an install with no enclosing checkout. Correcting it (resolving through the same build-context precedence, bounding the fetch with a timeout, and renaming the advice to the rebuild step) was considered and rejected: the notice is a git-state-dependent line on stdout that a later ticket converts the differential corpus into golden tests against, and an intermittent "Update available" depending on whether the developer's checkout happens to be behind `origin` is not goldenable. Deleting it from Go alone would have made the *bash* side of every corpus entry diverge under exactly that condition, so both bash launchers lost the function and its call site in the same change — the second sanctioned edit to the oracles, after ticket 09's `-H` notice. `USAGE.md`'s new *Updating* section replaces it: `git pull`, `make build`, then `--rebuild=full` when the image recipe changed.
- **Reading a container's environment reproduces the bash `jq` filter, including its failure modes.** All four tolerated locations are read and their lines *concatenated* (not first-match-wins); object members render in document order, so the decoder preserves member order rather than using a map; duplicate keys take the last value at the first position; a traversal error at a non-final path position discards the whole document — even paths that already succeeded — and stops everything after it, while keeping earlier documents' output. Values containing a newline become several lines, which is what keeps the two runtimes' output identical for the same logical environment. The golden table in `apple_inspect_test.go` was generated by running the extracted filter through `jq`, not by reading it. Only `jq`'s number canonicalization is deliberately not reproduced. Go needs no `jq`, so a `jq`-less host is one more place the two implementations legitimately disagree.
- **Docker-on-Linux liveness refuses rather than prompts.** Off macOS the daemon is a service, not an application: starting it is distro-specific and may need root, so the launcher diagnoses and exits instead of offering a `[Y/n]` whose "yes" branch cannot work. This is a deliberate divergence from `claude-docked`, which runs `open -a Docker` on a host with no `open` and then either dies with no message or polls forever; there is no oracle for the correct behavior. The macOS poll stays unbounded, matching bash.
- Tests: `internal/host`, `internal/plan`, `internal/runtime`, `internal/cli`, plus `tests/differential/harness.sh --compare REF:CANDIDATE` and the `CLAUDE_CONTAINED_TEST_TARGETS` override on the black-box suites.
